# Задача: горячее обновление рецептов HP_Crafter без перезапуска сервера

## Контекст проекта

Репозиторий: `dmitryfoll-del/kraftWB`  
Рабочая ветка: `main`

Нужно реализовать возможность менять рецепты в серверном файле `$profile:HP/HP_Crafter.json` без перезапуска DayZ-сервера. Изменения должны подхватываться при следующем взаимодействии игрока со столом крафта.

**Главное требование: не сломать существующую систему крафта, формат JSON, RPC и открытие интерфейса.** Сначала изучи текущий код и подтверждай используемые API. Не начинай переписывать архитектуру.

## Обязательный порядок работы

1. Изучи актуальное содержимое всех файлов, перечисленных ниже, непосредственно в репозитории.
2. Проследи полный путь данных: создание/загрузка JSON → хранение в `CraftServerManager` → отправка игроку → получение в `PlayerBase` → чтение интерфейсом `CraftHud`.
3. Проверь используемые Enforce Script / DayZ API по официальным источникам Bohemia Interactive или по достоверным исходникам DayZ.
4. Не выдумывай методы, сигнатуры, RPC-паттерны и типы. В частности, отдельно проверь фактическую сигнатуру и поведение методов `JsonFileLoader`, прежде чем использовать их.
5. Перед изменением покажи план и точный список файлов. Если работа ведётся в интерактивном режиме с владельцем репозитория, дождись его одобрения.
6. После одобрения внеси минимальные изменения. Не форматируй и не переписывай посторонний код.
7. Покажи diff по каждому изменённому файлу и объясни, что именно поменялось.
8. Не заявляй об успешной компиляции или тестировании, если они фактически не выполнялись.

## Текущее поведение, которое нужно сохранить

- При старте сервера вызывается `CraftServerManager.LoadData()`.
- Конфиг находится по пути `$profile:HP/HP_Crafter.json`.
- Если папки или файла нет, создаётся папка и стандартный JSON.
- Конфиг содержит объект `CraftServerManager`, внутри которого находится `m_CraftClasses`.
- При подключении игрока `MissionServer.InvokeOnConnect()` вызывает `g_CraftServerManager.SendTraderData(player)`.
- Данные отправляются существующим RPC `HPCc.SERVER_SEND_MAIN_DATA` как `Param1<ref CraftClasses>`.
- Клиент получает их в `PlayerBase.OnRPC()`, метод `ApplyServerData()` записывает данные в `PlayerBase.m_CraftClasses`.
- `CraftHud` читает категории и рецепты из `PlayerBase.m_CraftClasses`.
- Сейчас взаимодействие с `HP_Crafter` вызывает `g_CraftManager.SetHPC(ntarget)` и `g_CraftManager.RequestCraft()`; текущий `RequestCraft()` открывает UI сразу.
- Запрос выполнения рецепта использует `HPCc.CLIENT_REQUEST_CRAFT_ITEMS`. Его поведение менять нельзя.
- Существующие RPC `SERVER_SEND_MAIN_DATA`, `SERVER_SEND_CLOSE_MENU`, `CLIENT_REQUEST_CRAFT_ITEMS` и `CLIENT_REQUEST_FREE_WB` должны сохранить свои значения и назначение.

## Требуемое новое поведение

### При взаимодействии со столом в мультиплеере

1. Клиент сохраняет выбранный объект `HP_Crafter` в `g_CraftManager`.
2. Клиент отправляет серверу отдельный RPC-запрос на получение актуальных данных крафта.
3. До получения ответа интерфейс не открывается. Нельзя создавать `CraftHud` до того, как `PlayerBase.m_CraftClasses` получит актуальные данные.
4. Сервер получает запрос и проверяет его корректность: отправитель/игрок, наличие корректного объекта стола и допустимость взаимодействия с ним. Не доверяй клиенту без проверки. Используй только подтверждённые DayZ API для проверки существования объекта и расстояния.
5. Сервер пытается заново прочитать JSON в отдельный временный объект.
6. Только если чтение и необходимые проверки структуры прошли успешно, сервер заменяет текущую активную конфигурацию в памяти новой.
7. Если JSON отсутствует, повреждён, не читается или не проходит проверку, сервер сохраняет предыдущую рабочую конфигурацию в памяти. Не затирай её пустым или частично загруженным объектом.
8. После попытки обновления сервер отправляет игроку активную конфигурацию через существующий `SERVER_SEND_MAIN_DATA`. Если обновление не удалось, отправляется предыдущая рабочая конфигурация, если она доступна.
9. Клиент принимает ответ, обновляет `PlayerBase.m_CraftClasses` и открывает UI только если действительно ожидает ответ на запрос открытия стола.
10. Первоначальная отправка данных при подключении игрока остаётся. Получение данных при входе на сервер само по себе не должно открывать интерфейс.

### В одиночной игре

Сохрани работоспособность одиночной игры. Если текущая архитектура использует локальный `g_CraftServerManager`, обновляй данные локально и открывай меню только после успешного получения актуальных или сохранённых рабочих данных. Не отправляй сетевой RPC в одиночном режиме.

## Обновление конфигурации и безопасность данных

- Используй временный экземпляр `CraftServerManager` для чтения JSON.
- Не заменяй `m_CraftClasses` до подтверждения успешной загрузки.
- Проверь, как именно `JsonFileLoader` сообщает об ошибках в текущей версии DayZ. Не предполагай, что `JsonLoadFile` возвращает `bool`, и не используй `LoadFile` с придуманной сигнатурой.
- Если штатный загрузчик не позволяет надёжно определить ошибку, найди подтверждённый способ безопасной загрузки. Не добавляй самодельные API.
- Выполни разумную структурную проверку: объект данных, массив категорий и необходимые вложенные структуры должны быть доступны до замены активного конфига. Не вводи новые обязательные поля и не меняй JSON-схему.
- Не меняй исходный JSON автоматически при ошибке чтения. Не перезаписывай файл стандартными значениями при каждом открытии стола.
- Не добавляй непрерывный опрос файла, таймеры или циклическое чтение. Перечитывание происходит только по запросу открытия стола.
- Проверка времени изменения файла допустима только если найден и подтверждён реальный API DayZ. Она не обязательна: простой повторный разбор небольшого JSON при открытии стола предпочтительнее неподтверждённого API.
- Не добавляй whitelist SteamID, админ-команды или новые настройки доступа: они не нужны для этой задачи.
- Не меняй логику создания предметов, расходования ингредиентов, проверки рецептов, инвентаря и анимаций.

## Важные технические детали

- Клиентский RPC-запрос должен использовать подтверждённый проектом паттерн отправки client-to-server. В коде уже есть пример: `PlayerBase.RPCSingleParam(HPCc.CLIENT_REQUEST_CRAFT_ITEMS, ..., true, null)`. Проверь корректность применения этого паттерна для нового запроса.
- Ответ сервера должен адресоваться именно запрашивающему игроку через существующую отправку `SendTraderData(player)`.
- Учти, что `SERVER_SEND_MAIN_DATA` также приходит при подключении игрока. Поэтому `ApplyServerData()` не должен безусловно открывать меню.
- Не открывай UI, если данные не получены, `m_CraftClasses` отсутствует или список категорий пуст/непригоден для текущего интерфейса.
- Не допускай повторного открытия UI, если меню уже открыто или запрос уже выполняется.
- Убедись, что ссылка на выбранный стол остаётся валидной к моменту ответа сервера. Если объект удалён или недоступен, не открывай UI.
- Не меняй имена существующих классов и переменных без необходимости.

## Критерии приёмки

1. При первом запуске сервера создаётся стандартный `$profile:HP/HP_Crafter.json`, как и сейчас.
2. При последующих запусках существующий JSON не перезаписывается.
3. При подключении игрок получает данные как раньше, но UI автоматически не открывается.
4. При взаимодействии со столом UI открывается только после ответа сервера.
5. Если администратор изменил корректный рецепт в JSON, следующее открытие стола показывает новую версию без перезапуска сервера.
6. Изменения применяются и к уже подключённым игрокам при следующем открытии стола.
7. Если JSON повреждён или загрузка не удалась, последняя успешно загруженная конфигурация остаётся активной, и игрок получает её.
8. Если запрос некорректен или стол больше недоступен, UI не открывается.
9. Крафт по-прежнему использует существующие RPC и прежнюю серверную логику.
10. Одиночная игра продолжает работать.
11. Не изменена структура JSON и не удалены существующие категории, рецепты или настройки.
12. Нет неподтверждённых API, новых постоянных таймеров или фонового опроса файла.
